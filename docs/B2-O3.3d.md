# SmoothAF V2 — B2-O3.3d: contrato mínimo de coleta controlada

**Status:** investigação host-only concluída; contrato operacional e simulador validados. **NO-GO** para integração em `src/`, build ARM, commit, push ou coleta física nesta etapa.

A etapa aceita uma hipótese limitada: para uma série curta, a proveniência externa pode fornecer um escopo de análise suficientemente controlado sem exigir, imediatamente, um token global gerado pela câmera. Isso não cria identidade persistente, não cria identidade global e não prova independência dos frames YUV.

## Conclusão executiva

O contrato V1 pode ser usado para associação **local dentro de um artefato binário adquirido, imutável e declarado como uma única sessão**, desde que:

- o artefato original seja preservado;
- exista `source_id` externo não reutilizável;
- o SHA-256 seja calculado sobre o original antes da análise;
- a cadeia de transferência seja registrada;
- modo/contexto e fronteiras operacionais sejam conhecidos;
- artefatos misturados, truncados, duplicados ou sem metadata sejam rejeitados.

Isso é uma contenção operacional, não uma identidade de sessão no wire. O mesmo `episode_id`, `logical_id` ou timestamp em outro arquivo não pode ser associado ao primeiro.

**Importante:** o FIO atual não grava o fluxo binário de 36 bytes diretamente no arquivo. O fluxo real é:

```text
registro binário interno de 36 bytes
    -> ring RAM
    -> consumer/FIO
    -> formatação TSV
    -> arquivo SMTHnnn.LOG
    -> recuperação pelo PC
    -> análise host
```

O protótipo desta etapa modela **somente o fluxo binário V1**. Não foi implementado parser TSV. Portanto, a coleta física pode preservar o TSV original e sua provenance, mas a análise host dos arquivos físicos permanece bloqueada até existir um parser TSV aprovado ou uma extração binária lossless comprovadamente disponível. Não se deve presumir que o binário interno possa ser recuperado por USB.

## 1. Auditoria do ciclo real

### 1.1 Produção RAM e consumer

- `src/smoothaf_logger.c:147-183`, `smoothaf_persist_log_record()` — o produtor tenta lock sem bloquear, grava os 36 bytes no ring e publica o `head`. Lock ocupado ou ring cheio incrementa `dropped_count` e perde o registro.
- `src/smoothaf_logger.h:251-278` — o registro é 36 bytes; o ring tem 256 slots físicos e 255 utilizáveis; `sequence`, `build_id` e contadores são estado RAM.
- `src/smoothaf.c:2807-2809` — a tarefa AF publica somente registros RAM e não faz I/O de cartão.
- `src/smoothaf.c:3413-3437`, `smoothaf_fio_task()` — a tarefa FIO independente é dona do consumer e do handle de arquivo; executa o serviço aproximadamente a cada 20 ms.
- `src/smoothaf_logger_fio.c:419-487`, `smoothaf_log_fio_service()` — consome um batch, escreve, retém e tenta novamente uma falha, e só fecha quando o ring está vazio e não há batch pendente.

**Conseqüência:** a série curta reduz o risco de overflow, mas não o elimina. Um arquivo não é evidência completa se houver drop, erro, card ausente, task FIO não criada ou backlog não drenado. O contador de drops é diagnóstico auxiliar; os registros perdidos não podem ser reconstruídos.

### 1.2 Criação e nomes

- `src/smoothaf_logger_fio.h:22-25` define `ML/LOGS`, padrão `SMTH%03d.LOG`, máximo padrão de 9 arquivos e tamanho padrão de 256 KiB. O comentário da linha 22 usa um nome antigo, mas o padrão efetivo é `SMTH000.LOG` até `SMTH008.LOG`.
- `src/smoothaf_logger_fio.c:243-263`, `smoothaf_log_fio_get_next_filename()` — usa `get_numbered_file_name()` e procura o primeiro número livre.
- `src/smoothaf_logger_fio.c:266-305`, `smoothaf_log_fio_open_file()` — verifica cartão, escolhe o primeiro nome livre, chama `FIO_CreateFile()` e salva somente o basename em `current_filename`.
- `src/smoothaf_logger_fio.c:55-80` — o fallback host usa `fopen(..., "wb")`; a implementação não é append.

Arquivos existentes não são sobrescritos pela seleção normal. A numeração é **first-free**, não uma identidade monotônica: arquivos antigos consomem os números e, quando todos estão ocupados, novas escritas falham (`max_files_reached`). `file_index` e `total_files_written` não são persistidos no registro.

### 1.3 Abertura, escrita, rotação e fechamento

- `src/smoothaf_logger_fio.c:332-338` — a abertura é lazy, no primeiro batch; inicialização não cria arquivo.
- `src/smoothaf_logger_fio.c:319-416` — a escrita verifica card, gira antes de uma nova linha que excederia o limite e retenta short writes no mesmo arquivo.
- `src/smoothaf_logger_fio.c:356-375` — rotação fecha o arquivo atual e cria o primeiro próximo nome livre.
- `src/smoothaf_logger_fio.c:308-317` — `smoothaf_log_fio_close_file()` chama `FIO_CloseFile()` e limpa estado do handle.
- `src/smoothaf_logger_fio.c:180-212` — transição enable/disable fecha o handle e limpa retry; enable reseta apenas contadores do backend, não o ring RAM.

Não existe caminho de append de arquivo existente. Entretanto, o mesmo arquivo aberto recebe múltiplos batches e pode conter múltiplas sessões lógicas até rotação, disable ou shutdown.

### 1.4 Flush e durabilidade

- `src/smoothaf_logger.c:625-695` — `smoothaf_persist_log_consume_batch()` reserva e formata registros.
- `src/smoothaf_logger.c:721-786` — `smoothaf_persist_log_flush_batch()` escreve uma linha por vez; em erro restaura a cauda no primeiro registro não escrito.
- `src/smoothaf_logger_fio.c:235-241` — `smoothaf_log_fio_request_flush()` apenas levanta uma flag; não chama `fflush`, `fsync`, `FIO_Sync` nem outra garantia explícita de commit no cartão.
- `src/smoothaf_logger_fio.c:377-380` — `clean_d_cache()` é coerência de cache/DMA, não durabilidade.

Assim, “flush” significa drenar o batch do ring para `FIO_WriteFile()`. Não há prova no código de que o retorno do write seja um commit durável antes de power loss.

### 1.5 Sessões no mesmo arquivo

- `src/smoothaf.c:982-998`, `smoothaf_persist_session_start()` — emite `SESSION_START` somente se o logger está habilitado e a latch de sessão está inativa.
- `src/smoothaf.c:1000-1016`, `smoothaf_persist_session_end()` — emite `SESSION_END`, mas ignora a falha de aceitação do registro e limpa a latch mesmo assim.
- `src/smoothaf.c:1452-1477` — início automático no Movie/REC.
- `src/smoothaf.c:3833-3851` — início manual do monitor.
- `src/smoothaf.c:2819-2822` — término da tarefa publica o fim.
- `src/smoothaf.c:1490-1504` — parada automática delega normalmente a ordenação final ao monitor.

`SESSION_START`/`SESSION_END` não fecham nem giram o arquivo. Portanto, **um arquivo não corresponde automaticamente a uma sessão**. Pode conter múltiplas sessões, e um crash/power loss pode deixar uma sessão sem `SESSION_END`.

### 1.6 Reinício do módulo e da câmera

- `src/smoothaf_logger_fio.c:130-163` — `smoothaf_log_fio_init()` zera completamente o backend.
- `src/smoothaf.c:5406-5425` — `smoothaf_init()` zera logger/FIO e reinicia estado RAM.
- `src/smoothaf_logger.c:804-809` — `smoothaf_persist_logger_init()` zera `sequence`, ring e estado.
- `src/smoothaf.c:5479-5541` — deinit solicita close, mas não espera indefinidamente por I/O.
- `src/smoothaf.c:3429-3437` — shutdown do FIO é deliberadamente não-draining; registros ainda no RAM podem ser perdidos.

Após reinício da câmera, os arquivos no cartão permanecem e a próxima execução escolhe outro primeiro nome livre, mas `sequence`, episode IDs, contadores e latch de sessão recomeçam. Não existe boot ID nem marcador de recuperação de power loss.

## 2. Informação preservada pelo TSV real

`src/smoothaf_logger.c:586-623`, `format_record()`, serializa cada linha como:

```text
timestamp_ms<TAB>event_name<TAB>episode_id<TAB>payload[0]...<TAB>payload[5]
```

A conversão preserva:

- ordem física das linhas;
- timestamp monotônico;
- nome do evento;
- `episode_id`;
- seis payloads, respeitando conversão signed/unsigned por evento.

A conversão perde ou não inclui:

- `sequence` do registro;
- `build_id` copiado para `buf->build_id` em `smoothaf_logger.c:190-205`;
- número do arquivo como campo do registro;
- namespace/generation de observabilidade;
- identidade persistente de sessão;
- estado do ring, drops e motivo de uma ausência de linha, salvo eventos/counters específicos que também podem sofrer drop.

Para `OBS_SNAPSHOT_V1`, o TSV preserva em princípio o `event_name`, `episode_id`, timestamp e os seis slots que permitem reconstruir o payload V1. Porém, a associação ainda depende de um parser TSV que valide o formato e de provenance externa. A perda de `sequence` não impede sozinha o pareamento por `(episode_id, logical_id, phase)`, mas impede usar a ordem global RAM como evidência adicional.

**Limitação atual:** `tools/b2o32_serialization.py` e o novo `tools/b2o33d_collection.py` aceitam apenas o stream binário de 36 bytes. Não há afirmação de que um `SMTHnnn.LOG` real possa ser alimentado diretamente nesses módulos.

## 3. Contrato mínimo de coleta controlada

### 3.1 Artefato original

Para cada arquivo transferido, preservar sem edição:

- nome original completo, por exemplo `ML/LOGS/SMTH017.LOG`;
- cópia byte a byte somente leitura no host;
- SHA-256 calculado imediatamente sobre essa cópia;
- tamanho em bytes;
- listagem do diretório antes/depois, sem remover o SD;
- indicação se o arquivo foi copiado por leitor de cartão, USB ou outro caminho — sem inferir que USB fornece o ring binário;
- cadeia de transferência (`camera-card -> read-only-copy -> host-analysis`).

O SHA-256 prova integridade da cópia contra o artefato que foi hashado. Não prova que o arquivo era uma única sessão nem que não foi misturado antes do hash.

### 3.2 `source_id`

`source_id` deve ser criado no host para aquela aquisição imutável, por exemplo uma combinação registrada de:

```text
<acquisition-id>/<original-relative-path>/<sha256>
```

O identificador não deve ser apenas `SMTH017.LOG`, porque o nome é reutilizável em cartões/acquisitions diferentes. Um `source_id` já encerrado não pode ser reutilizado no parser.

### 3.3 Manifest mínimo

O manifest externo deve conter, sem preencher ausências:

```text
artifact_format       = binary-v1 ou tsv-preserved-unparsed
original_filename     = nome original
source_id             = identificador externo não reutilizável
expected_sha256       = hash esperado, retido independentemente
observed_sha256       = hash calculado da cópia recebida
size_bytes            = tamanho esperado e observado
mode                  = H264_REC_ON
run_mode              = DRY_RUN
lens_motion           = PROHIBITED
camera_context        = modelo/firmware/build conhecido, se disponível
start_known           = true/false/unknown
end_known             = true/false/unknown
session_scope         = SINGLE_SESSION/MULTI_SESSION/CONCATENATED/UNKNOWN
transfer_chain        = passos de transferência
marker_state          = ABSENT/COMPLETE/PARTIAL/CONTRADICTORY
```

`build_id` pode ser anexado como provenance do software se for obtido de fonte externa confiável, mas não é identidade da câmera/sessão e não pode ser inventado a partir do nome do arquivo.

### 3.4 Política de aceitação

O contrato D não aceita `OBS_SESSION_START`/evento 25: se ele aparecer no stream binário, o artefato é `FORMAT_UNSUPPORTED` e deve ser encaminhado ao parser específico da B2-O3.3c. Um marker malformado não é registro histórico opaco.

Aceitar para associação V1 somente um artefato binário integral que tenha:

- formato conhecido;
- comprimento múltiplo de 36 bytes;
- todos os registros decodificáveis;
- hash correspondente ao original;
- `source_id` novo;
- modo/contexto completos;
- início e fim conhecidos;
- `session_scope=SINGLE_SESSION` explicitamente assegurado pelo procedimento.

Rejeitar com `IDENTITY_UNAVAILABLE`, `INCOMPLETE_ARTIFACT`, `INTEGRITY_FAILURE` ou `AMBIGUOUS_PAIR` quando houver falta de metadata, hash divergente, truncamento, arquivo misturado, concatenação, source duplicado, marker parcial/contraditório ou escopo desconhecido.

A declaração `SINGLE_SESSION` é uma garantia operacional do procedimento, não uma prova criptográfica. Se a análise dos eventos posteriormente encontrar duas sequências de sessão ou outra contradição, o artefato deve ser rebaixado a ambíguo e nenhum par deve ser promovido. Um prefixo truncado que termina exatamente em um limite de 36 bytes continua rejeitado se o comprimento/completude esperados não forem independentemente confirmados; hash calculado sobre o próprio prefixo não prova que ele era completo.

## 4. Procedimento proposto para 5–10 medições

Este procedimento é uma proposta para autorização futura, não uma autorização física atual.

1. Fixar o build aprovado e registrar o contexto externo: câmera/firmware, modo H.264 REC ON, DRY RUN, lente imóvel, configurações relevantes e data/hora do operador apenas como metadata, nunca como identidade.
2. Antes da coleta, listar e fotografar/copiar a árvore `ML/LOGS`; não remover o SD nem apagar arquivos antigos.
3. Confirmar logger persistente e FIO habilitados e que o FIO task iniciou; registrar os indicadores disponíveis. Se o task falhar, rejeitar a coleta.
4. Isolar uma única janela operacional: 5–10 medições, sem troca de sessão, sem reinício, sem rotação intencional, sem movimento de lente e sem outra atividade que produza logs concorrentes.
5. Registrar externamente as ações de início e fim. O operador não deve declarar `end_known=true` se houve power loss, task não encerrada, card warning, FIO error, partial write ou shutdown não observado.
6. Encerrar de forma limpa e aguardar o indicador externo de que o FIO task saiu/fechou. Como o código é não-draining, ausência de confirmação implica artefato incompleto.
7. Sem alterar o cartão, fazer a aquisição read-only do arquivo original e de sua listagem. Se aparecer mais de um arquivo novo por rotação, tratar cada arquivo como source separado e não cruzar pares entre eles sem um vínculo externo explícito.
8. Calcular SHA-256 no host, criar o manifest e preservar uma cópia mestre. Não renomear a cópia mestre; qualquer nome de trabalho deve ser derivado.
9. Não analisar um `SMTHnnn.LOG` real com o parser binário. Nesta etapa, classificar o TSV como `tsv-preserved-unparsed`; a análise V1 física aguarda parser TSV ou uma extração lossless aprovada.

A exigência de uma única sessão não pode ser deduzida apenas do nome do arquivo. Mesmo com uma única sessão planejada, se a abertura/fechamento do FIO não for observável, a coleta deve permanecer `UNKNOWN`/rejeitada.

## 5. Identidade no wire e limites

| Propriedade | V1 + coleta controlada | O que não prova |
|---|---|---|
| Pareamento local | Pode ser seguro dentro do artefato validado, com boundary externo e chave V1 válida. | Não prova que outro arquivo com a mesma chave pertence à mesma sessão. |
| Identidade entre sessões | Não existe no wire; o `source_id` separa aquisições. | Não é boot ID nem session UUID. |
| Identidade global | Não existe. | Hash, filename e build ID não tornam a câmera globalmente identificável. |
| Independência YUV | Não provada. | BEFORE/AFTER podem observar o mesmo frame ou frames não independentes. |
| Integridade | SHA-256 verifica a cópia do artefato. | Não verifica completude sem limites observáveis nem ausência de mistura prévia. |

`timestamp`, `sequence` (quando presente no binário), `episode_id` e `logical_id` continuam sendo metadados locais. Não devem ser usados para inferir identidade após reinício ou entre arquivos. Drops, wraps e recomeços mantêm o resultado incompleto/ambíguo.

## 6. V1 controlado versus evento 25

| Aspecto | V1 + provenance controlada | `OBS_SESSION_START` + metadata externa |
|---|---|---|
| Firmware agora | Nenhuma alteração. | Exige novo evento e emissão de token; não autorizado nesta etapa. |
| ABI/histórico | Preserva 36 bytes e eventos existentes. | Também pode preservar 36 bytes, mas consome um slot do ring. |
| Custo no ring | Zero adicional. | Um registro por sessão, sujeito a drop. |
| Série curta | Suficiente para escopo local se uma única sessão for realmente controlada. | Confirma token no wire quando não perdido; valor adicional pequeno. |
| Falha de boundary | Rejeitar o arquivo/pareamento. | Marker sozinho não resolve arquivo copiado/concatenado sem provenance. |
| Reinício | Novo `source_id`; nunca cruzar automaticamente. | Novo token necessário, mas fonte global continua não demonstrada. |
| Perda de início/fim | Tratada como incompleta; não inferir. | Marker perdido pode ser recuperado apenas com token externo exato. |
| Recuperação | Hash e cópia original permitem repetir análise; não reconstroem registros. | Mesmo requisito, mais token se preservado. |
| Rollback | Nenhum código de produção a reverter. | Desativar emissão mantém V1, mas exige migração adicional. |
| Valor diagnóstico imediato | Alto para testar formato/proveniência e uma série curta, condicionado ao parser TSV. | Maior para futuras sessões, não necessário para o primeiro ensaio controlado. |

Para o experimento curto, a menor mudança necessária no firmware é **nenhuma**. O bloqueio prático é o formato: os arquivos físicos atuais são TSV e não há parser TSV host nesta etapa.

## 8. Recomendação para B2-O3.3

### GO condicional para coleta futura

Pode-se preparar uma coleta controlada curta sem adicionar `OBS_SESSION_START`, desde que a autorização futura aceite explicitamente que:

1. o objetivo inicial é validar o caminho de provenance e o comportamento observável, não afirmar identidade global;
2. cada artefato tenha manifest e hash antes da análise;
3. nenhum arquivo TSV real seja tratado como binário V1;
4. sem parser TSV aprovado, o resultado físico seja apenas **coleta preservada, análise pendente**;
5. qualquer dúvida sobre mistura, truncamento, drop, FIO shutdown ou fronteira vire rejeição.

### NO-GO atual

- **NO-GO para commit:** alterações permanecem não commitadas conforme solicitado.
- **NO-GO para preparação de build ARM:** nenhuma integração nova foi autorizada.
- **NO-GO para finalizar B2-O3.3 passiva:** o TSV físico ainda não é consumível pelo parser host V1; falta decidir/implementar posteriormente um parser TSV ou formato binário exportável. O contrato D aceita somente `binary-v1`; um arquivo TSV físico é preservado como `tsv-preserved-unparsed` e rejeitado para pareamento.
- **NO-GO para alegar identidade persistente/global ou frame independence:** provenance externa não muda essas limitações.

A alternativa mínima para o primeiro experimento físico é, portanto, **coletar e preservar com provenance controlada, sem promover pares até que a representação TSV seja decodificada e validada**. O evento 25 continua uma melhoria futura, não um requisito para esta série curta nem uma autorização para produção.
