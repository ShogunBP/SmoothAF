# SmoothAF V2 — B2-O3.3f: consolidação final de observabilidade

## Escopo e status

Revisão consolidada das alterações locais B2-O3.3 até B2-O3.3e. Nenhum commit ou push foi executado. Não houve instalação na Canon T3i, D1 físico, ACTIVE CONTINUOUS, HOLD, shadow mode, movimento de lente ou build ARM do módulo.

## Elegibilidade por finalidade

As propriedades não são colapsadas em um único booleano:

| Propriedade | Significado | Política |
|---|---|---|
| validade estrutural TSV | nove campos, ASCII, LF final, ranges e payload decodificável | necessária para qualquer uso |
| par completo | BEFORE e AFTER do mesmo `(episode_id, logical_id)` dentro do boundary local | necessário para análise do par; duplicado/incompleto é rejeitado |
| provenance | `source_id`, hash, tamanho, contexto, cadeia e fronteiras conhecidas | necessária para aceitar a cópia local |
| identidade de sessão | identidade persistente/global demonstrada | indisponível no TSV V1 |
| independência YUV | prova de frames distintos | `false`; nunca inferida de timestamp ou par |
| análise descritiva | descrição local do artefato validado, sem generalização operacional | `ACCEPT_LOCAL` quando parser/provenance não têm rejeições |
| calibração operacional | mudança de limites, comportamento ou decisão do firmware | `REJECT` nesta etapa |

Assim, um arquivo íntegro e localmente identificado pode produzir métricas descritivas e contagens mesmo quando o escopo de sessão é desconhecido, desde que a análise não atravesse boundaries nem promova pares; pares estruturais só valem dentro do boundary local. Ele não pode provar identidade global, independência de frame, nem fundamentar calibração operacional. Um par estrutural não compensa provenance ausente; `MULTI_SESSION`, concatenação indistinguível, drops, truncação, linhas inválidas, hash divergente e source duplicado permanecem fail-closed para pareamento.

## Auditoria do TSV real

O consumer de `src/smoothaf_logger.c` usa `format_record()` para produzir:

```text
timestamp_ms<TAB>event_name<TAB>episode_id<TAB>payload[0]<TAB>payload[1]<TAB>payload[2]<TAB>payload[3]<TAB>payload[4]<TAB>payload[5]<LF>
```

Não há cabeçalho e não há `sequence`. O parser preserva bytes, offsets, números de linha e ordem física. `OBS_SNAPSHOT_V1=24` é decodificado por reutilização do decoder V1, mas a ausência de sequence permanece `None`.

A tabela signed/unsigned foi verificada contra o C:

- `D1_SERIES_START`, slots 0–2 unsigned;
- `D1_SERIES_END`, todos os slots unsigned;
- `D1_CONTEXT`, `D1_CONTEXT_AUX`, `MOVIE_GATE_REJECT`, todos os slots unsigned;
- `D1_SAMPLE`, slot 0 unsigned;
- demais payloads signed.

O C imprime `UNKNOWN` tanto para o tipo 0 quanto para tipos não reconhecidos. Logo, `UNKNOWN` é opaco e não pode ser promovido a tipo 0 ou evento 25.

## Integração B2-O3.3

- `SMOOTHAF_OBSERVABILITY_ENABLED` é `0` por padrão em `src/smoothaf_observability.h`.
- Com OFF, os estados/callbacks/chamadas de observabilidade são removidos pelo pré-processador; a seam original mantém uma única chamada `get_yuv422_vram()`, a mesma ROI, `smoothaf_measure_all()`, métricas e decisões.
- Com ON, o observador reutiliza o ponteiro `vram` existente e apenas captura metadados CORE. Não há segunda chamada YUV, leitura de MVR real, dereference de `0x1e44`, `lens_focus()` no observer ou publicação de comandos.
- Namespaces/generations são proteção em memória; não alteram o ABI de 36 bytes nem são persistidos.
- STOP/PANIC, gates Movie/REC, budgets, recovery e lifecycle existente permanecem no controlador. O observador só tenta publicar no ring e não introduz movimento.
- Logger e FIO continuam separados. Publicação/flush são best-effort; falha de lock, ring cheio, logger desligado ou erro de FIO não bloqueia a medição. O shutdown continua não-draining.
- `integration/Makefile` inclui apenas o novo objeto; `build-smoothaf.ps1` copia e testa os dois arquivos C do observador.

## Evidência C → TSV → Python

Foi adicionado um harness específico, diferente do fixture manual:

- `tests/test_smoothaf_logger_tsv.c` insere nove registros no logger C real, chama `smoothaf_persist_log_consume_batch()` e imprime as linhas formatadas;
- `tests/check_smoothaf_logger_tsv.py` lê essas linhas e chama `tools/b2o33e_tsv.py`;
- a verificação cobre signed/unsigned, `OBS_SNAPSHOT_V1`, timestamps `0`/`UINT32_MAX` e `UNKNOWN`;
- resultado: **`C formatter TSV -> Python parser equivalence passed`**.

A equivalência binária C↔Python também passou no harness existente. O teste host completo via `build-smoothaf.ps1 -TestOnly` executou os testes C, o harness textual novo, o wire check, testes de logger/FIO, regressões e benchmarks simulados.

## Limitações e riscos

1. TSV perde `sequence`, build ID serializado, drops implícitos e identidade persistente.
2. `SESSION_START`/`SESSION_END` são lifecycle e podem estar ausentes, duplicados ou sofrer drop; não são UUID.
3. Hash verifica a cópia, não prova que o conteúdo não estava misturado antes do hash.
4. A classificação CORE não prova independência de frames YUV; os dois snapshots podem observar o mesmo frame.
5. O caminho FIO não fornece garantia explícita de durabilidade antes de power loss; shutdown não-draining pode perder registros.
6. A auditoria é host-only: não valida símbolos, ABI efetivo, timing ou disponibilidade de VRAM no Legacy 600D.102.
7. O C formatter não permite recuperar o tipo numérico 0 versus desconhecido, porque ambos viram `UNKNOWN`.

## Riscos relevantes para Legacy 600D.102

O risco principal é de integração de build/símbolos e comportamento temporal do Legacy, não do parser host. Por isso o default OFF é conservador. A compilação ARM precisa ser separada da decisão de commit e exige o Legacy tree/symbol source aprovados; nada disso foi executado nesta revisão.

## Rollback mínimo

1. Para o host: não usar os novos módulos e manter análise histórica existente.
2. Para a integração: remover `smoothaf_observability.o` de `integration/Makefile`, parar de copiar `smoothaf_observability.c/.h` no script e remover as chamadas protegidas em `src/smoothaf.c`, preservando o evento 24 apenas se a política de logs exigir compatibilidade; ou recompilar com `SMOOTHAF_OBSERVABILITY_ENABLED=0` para desativar a instrumentação.
3. Nenhum dado histórico exige migração: o ABI continua `<IHHI6i` e o parser rejeita/ignora evidência que não consegue demonstrar.
4. A reversão deve ser feita antes de qualquer instalação física; não há necessidade de apagar logs do cartão.
