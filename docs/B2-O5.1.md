# SmoothAF V2 — B2-O5.1: reusable OBS ON experimental test plan

## Status and scope

This document is the host-side operational plan for a future Canon EOS 600D / Rebel T3i session. It is deliberately reusable: one verified module installation is retained while the operator selects the tests that are technically permitted and useful for that session.

No camera, SD card, lens, USB transfer, or ARM build action was performed while preparing this plan. The plan is not a physical-test authorization and does not replace the separate approval required for a future installation.

The plan does **not** add an administrative prohibition to any implemented SmoothAF mode. The mode table below records technical gates from the existing build. Administrative approval, scene choice, and whether the operator elects to run a row are separate decisions.

## 2. Mode availability and technical gates

All rows are available in the module. “Movement” describes the existing implementation, not a new policy.

| Mode/control | Lens movement | Technical start conditions | Normal completion / stop behavior |
|---|---:|---|---|
| Monitor (`Vlog Monitor > Monitoring`) | No by itself | LiveView measurement path, no competing owner/task, no STOP/PANIC. It may run with AF mode OFF or with an AF mode selected. | Toggle off, STOP/PANIC, recording/session transition, error, or task completion. The monitor owns the shared measurement gate while running. |
| DRY RUN | No; controller requests are simulated and must report `DRY_RUN` with zero lens calls | Monitor running; `Vlog AF Mode=DRY RUN`; LiveView; normal measurement/recording gates. H.264 Movie is allowed only when the existing H.264 Movie Dry Run gate accepts it; custom/RAW and conflicting focus controllers remain blocked. | One bounded episode, gate rejection, timeout, STOP/PANIC, or monitor stop. Verify `AF Lens Calls=0`; a zero-call result is required evidence, not an assumption. |
| ACTIVE | Yes | `Enable=ON`; `Vlog AF Mode=ACTIVE`; monitor running; manual `Start New AF Episode`; LiveView; no manual/continuous/follow/rack/stack focus exclusion; no competing task. In Movie/recording, the existing experimental H.264 gate also requires `Movie Active Exp=ON`, normal H.264, and the other Movie gates. | Bounded episode result such as `CONVERGED`, `SEARCH_LIMIT`, `TIMEOUT`, `BLOCKED`, `CANCELLED`, or lens/measurement error. STOP/PANIC cancels cooperatively. |
| ACTIVE CONTINUOUS | Yes | `Enable=ON`; `Vlog AF Mode=ACTIVE CONTINUOUS`; monitor running and continuous authorization armed. Episodes start only when the existing reference/blur, acquisition, cooldown, task, and safety gates allow them. H.264 recording-edge automatic start additionally requires `Movie Active Exp=ON`, LiveView, normal H.264 Movie, no competing focus controller, and no active monitor conflict. | Repeated bounded episodes while the latch and cooldown rules permit them. Recording end, monitor stop, STOP/PANIC, safety pause, error, or task shutdown ends the run. Known hunting is an experimental limitation to observe, not a permanent mode prohibition. |
| D1 Collect | No | `Diagnostic > D1 Collect`; LiveView; no STOP/PANIC; no active task/monitor/episode/Focus Test/measurement owner; the existing measurement gate must accept the current context. REC OFF is the baseline. H.264 REC ON is optional only when the existing gate accepts it, normally with `Vlog AF Mode=DRY RUN`; custom/RAW and excluded focus-controller states remain rejected. | Exactly 30 requested samples, or cancellation/context/error termination. D1 cadence is clamped to 100–120 ms and its actual duration is not fixed. |
| Focus Test | Yes | `Enable=ON`; `Focus Test > Start Focus Test`; selected Legacy HC, Adaptive HC, or Normal AF; LiveView; no monitor or competing task; existing Movie/recording/manual-focus/focus-controller gates must pass. The test has its own algorithm, metric, direction, step, timeout, command, and reversal controls. | Lock, no confidence, limit, timeout, cancellation, lens error, or measurement error. STOP/PANIC cancels future work; do not unload while its task is active. |
| Focus Step | Yes | `Enable=ON`; `Diagnostic > Focus Step`; valid direction and step 1–3; LiveView; no competing owner/task; existing movement gates must pass. | STOP | No new movement | Always available as a cooperative cancellation request. | PANIC / Emergency Stop | No new movement | Emergency control does not acquire the shared semaphore. | Logger FIO Enable | No | Requires Persistent Logger ON. The independent FIO task owns card I/O and writes `ML/LOGS/SMTHxxx.LOG`. | Keep enabled while draining; disable only after the ring is empty and counters have been recorded. FIO shutdown is non-draining. |

Technical gates are fail-closed. A gate rejection is a valid test observation and must not be worked around by changing the source, compile-time default, or safety mechanism.

## 3. Observable seams and records

### D1 and OBS

D1 is a distinct diagnostic lifecycle, not DRY RUN. It requests exactly `SMOOTHAF_D1_MAX_SAMPLES = 30` samples and calls the existing `smoothaf_measure_with_metric()` seam. In OBS ON, that seam captures BEFORE and AFTER snapshots around the existing metric calculation. The observer is passive: it does not call `lens_focus()` and does not publish a movement command.

The following are separate paths:

- D1 lifecycle records: events 18–22 (`D1_SERIES_START`, samples, end, context, and context auxiliary data).
- OBS event 24 (`OBS_SNAPSHOT_V1`): emitted only when OBS is enabled, the pair is classified/serialized, the persistent logger is enabled, and the non-blocking ring publication succeeds.
- A D1 sample count of 30 therefore does not guarantee 30 persisted TSV lines or 30 event-24 records.

### AF and monitor evidence

For every selected AF or monitor row, record at least:

- Build ID, mode, algorithm, metric, direction, step, LiveView and recording state;
- monitor/task state and the reason for every gate rejection;
- `AF Move Attempts`, `AF Lens Calls`, `AF Move Successes`, last block and last move result;
- episode result/reason, command count, score/best score/delta, position, confidence, cooldown and episode count;
- STOP/PANIC action and the final task state.

`AF Lens Calls=1` proves that `lens_focus()` was invoked; it does not by itself prove physical displacement. Conversely, DRY RUN must show zero calls for a valid no-movement result.

## 4. Reusable test procedure

### Phase A — initialize once

1. Before card handling, make and verify a complete SD backup. Record camera model, firmware, Legacy Lua Fix revision, lens, card identity/state, battery state, and the test operator.
2. Copy only the verified OBS ON module to the normal module location during the separately approved installation. Do not replace firmware, `AUTOEXEC.BIN`, loader files, or other modules.
3. Boot once. Confirm the exact Build ID `d9efe064845a-600D.102-obs-on`, module load, menu presence, and no lens activity caused by loading. If identity or load state is wrong, stop and classify the session as a package/runtime failure.
4. Confirm the startup baseline: `Enable=OFF`, `Vlog AF Mode=OFF`, no monitor/task/episode, PANIC clear, and logger/FIO disabled unless the session is intentionally starting Phase B. Open read-only diagnostics first.
5. Exercise menu visibility without starting a task. Confirm `STOP`, `PANIC`, and `Rearm Safe Mode` are present. Do not use Rearm until a real PANIC test has a confirmed task exit.
6. Record the initial Runtime Diagnostics and Build Info values, including task and semaphore state. This is runtime evidence; the host artifact hash remains the package identity.

Do not reinstall, replace the module, or reboot between selected rows unless the operator has intentionally ended the session or a recovery decision requires it.

### Phase B — logger, passive measurements, and optional H.264 observation

1. Enter `Diagnostic` and enable `Persistent Logger`. Then enable `Logger FIO Enable`. Wait for the runtime page to show the requested logger/FIO state applied and the FIO task running. Record initial fill, published/flushed counts, drops, FIO errors, partials, files, bytes, and any pending/config state.
2. Start with LiveView, REC OFF, `Enable=OFF`, `Vlog AF Mode=OFF`, and no monitor or AF episode. Run one `D1 Collect`.
3. During D1, record the series ID, active/terminal state, requested/produced count, cadence, timestamps, valid/confident counts, drops, errors, gaps, partials, and foreign-producer count. Wait for the terminal status; do not infer completion from elapsed time alone.
4. Confirm no movement evidence: D1 must not increment `AF Lens Calls`, issue a move, or enter an AF episode. If any movement or unexpected task activity occurs, press PANIC, wait for task exit, and abort the collection.
5. If the existing gate is observed to permit it and the operator elects the optional case, use normal H.264 recording with `Vlog AF Mode=DRY RUN`, `Enable=OFF`, and no physical AF action. Start REC, attempt the passive D1/DRY RUN observation, and record either accepted data or the exact gate rejection. Do not relax a rejection. Custom/RAW recording and excluded focus-controller states remain technical blockers.
6. Between passive series, wait for the task to exit and verify the logger is servicing the ring. Keep the same module installed and preserve all generated original log files.

### Phase C — operator-selected AF rows

The operator may select any subset of these rows. There is no required order beyond the common precondition that the previous task has exited and the shared gate is free. Use short, controlled trials first and retain the same installation.

#### C1 — ACTIVE

1. Use photographic LiveView, REC OFF, no competing focus controller, and a controlled scene.
2. Set `Enable=ON`, select `Vlog AF Mode=ACTIVE`, choose the existing algorithm/metric/direction/step, start `Monitoring`, and select `Start New AF Episode`.
3. Record the fields in the AF evidence list. Verify that every physical command remains within the displayed bounded command/session/reversal limits.
4. End with the episode's normal result or use STOP. Use PANIC if unexpected movement or another emergency condition occurs.

For H.264 Movie, the existing path remains available only when its technical conditions are true: normal H.264, LiveView, `Movie Active Exp=ON`, `Enable=ON`, ACTIVE/ACTIVE CONTINUOUS mode, and no excluded focus controller. Custom/RAW and unsupported states must be rejected by the existing gate.

#### C2 — Focus Test

1. Return to a task-free state, use photographic LiveView and REC OFF, and keep Vlog AF independent from the Focus Test.
2. Set `Enable=ON`, select `Focus Test > AF Algorithm`, `Test Metric`, `Test Step`, and `Test Direction`, then select `Start Focus Test`.
3. Record initial/final scores, algorithm phase, best position, commands, reversals, duration, result, last block, lens return, and measurement validity.
4. Use STOP for cooperative cancellation. Do not unload or replace the module until the task state is `IDLE`/exited.

#### C3 — Focus Step

1. Return to a task-free photographic LiveView state with `Enable=ON`.
2. Select `Diagnostic > Direction`, choose the direction, and select `Focus Step` with the existing step value 1–3.
3. Record the command, lens return, settle/measurement result, score, task state, and any block reason. This is a physical movement test, not a D1 or DRY RUN test.

#### C4 — ACTIVE CONTINUOUS

1. Use the existing monitor and continuous controls: `Enable=ON`, `Vlog AF Mode=ACTIVE CONTINUOUS`, start monitoring, and arm the continuous episode through the existing menu path. For automatic H.264 recording-edge behavior, use only the existing H.264 Movie gate and `Movie Active Exp=ON`.
2. Observe the monitor state, reference state, possible-blur latch, acquisition counters, cooldown/recheck state, episode boundaries, and command limits. Do not assume that selecting the mode immediately commands the lens; the existing state machine waits for its start conditions.
3. Monitor the known hunting limitation. If hunting, unexpected movement, recording corruption, task stall, heat, battery, or card warning appears, use PANIC immediately. A synchronous `lens_focus(wait=1)` already in progress may complete before the stop is visible.
4. End by STOP, PANIC, recording end, monitor stop, or normal safety/result transition. Wait for the monitor task and any FIO activity to reach the shutdown criteria before proceeding.

### Phase D — cooperative shutdown and one batch recovery

1. End the selected episode(s) with STOP or the normal terminal result. Stop the monitor. Confirm no `smoothaf_task` remains running and `task_exited` is true. If not, wait; do not unload, reload, or power-cycle the camera while a task remains active.
2. Keep Persistent Logger and FIO enabled while the consumer services the ring. Observe fill until it is zero and compare published/flushed counts. Record drops, errors, partials, current file, file count, and bytes written.
3. There is no operator-visible blocking flush in this build. Any internal/requested flush is non-blocking and is not an `fsync` or durability guarantee. The operational requirement is to keep FIO running, observe the ring drain, and verify counters; do not claim that a flush alone makes data durable.
4. After the ring is empty and counters are recorded, disable FIO and then the logger through the existing menu. Wait for the configuration request to be applied and for the FIO backend to close. If a close or task state cannot be confirmed, classify the data as incomplete/unknown and do not unload.
5. If the module is deinitialized, remember that deinit is deliberately non-draining. It requests FIO close and returns a failure/unload-hazard state if a worker remains active. Leave the module/menu in place until the task and FIO exit indicators are quiescent.
6. Power down only after the camera is in the intended safe state. Recover all original `ML/LOGS/SMTHxxx.LOG` files once, in one batch, preferably with a read-only card-reader workflow. Preserve names and bytes, compute host hashes before parsing, and keep the original copies immutable.

## 5. Result classification

### Success

A row is a **runtime success** when its expected terminal behavior and technical gates are observed, the task exits, and the relevant counters/telemetry are recorded. D1 additionally requires a normal 30-sample terminal status for a complete D1 run.

A collection is **data-complete for analysis** only when the recovered original files are intact and locally identified, there are no unexplained drops/errors/partials, the ring was drained before shutdown, and the transfer hashes match the recovered bytes. This does not establish global session identity or independent YUV frames; those remain the documented TSV limitations.

### Failure / abort

Abort immediately for unexpected lens movement during a passive test, a Build ID mismatch, recording corruption, task stall, abnormal heat, battery/card warning, unsafe state, or a logger/FIO error that cannot be understood. Use PANIC for an emergency, then wait for task exit. Do not unload or replace the module during an active or unknown task state.

### Inconclusive or incomplete data

Classify the row as **INCONCLUSIVE** rather than successful when a gate rejects it, the runtime ABI/task state is not trustworthy, D1 ends by cancellation/context/error, the logger was disabled, the ring dropped records, FIO reported errors/partials, the close/exit state was not observed, the card was removed before controlled shutdown, or USB/card transfer integrity is unknown. A gate rejection is evidence of the existing gate, not permission to bypass it.

## 6. SD handling and USB limitation

The minimum-intervention strategy is:

1. one verified SD backup;
2. one installation of the dated OBS ON module;
3. many selected rows using that same loaded module;
4. no per-test log deletion, rotation, replacement, or SD removal;
5. one controlled shutdown;
6. one batch recovery and one host-side hash/parse pass.

The package writes `ML/LOGS/SMTHxxx.LOG` through the existing FIO path. The repository has no proven Canon USB/PTP/MTP path for retrieving these Magic Lantern log files. Do not assume that a camera USB connection exposes `ML/LOGS`, and do not add firmware USB export for this stage. If USB is investigated later, treat it as a separate experiment; the card-reader batch recovery remains the operational fallback.

## 7. Known limitations and decision

- This package proves host-side preservation, the recorded ARM build checks, and static contracts; it does not prove the camera ABI, DryOS scheduling, VRAM behavior, lens response, H.264 behavior, card durability, or USB recovery.
- OBS event 24 is conditional on classification, logger enablement, and ring publication. Produced, ring-stored, and TSV-persisted records are different evidence classes.
- The ring is finite (255 usable 36-byte records); producer contention/full conditions can increment drops. FIO batches are bounded and short writes/errors remain retryable, but shutdown is non-draining.
- `lens_focus(wait=1)` may continue after STOP/PANIC. Emergency controls preserve cancellation and ownership but do not guarantee immediate interruption of a synchronous call.
- ACTIVE CONTINUOUS hunting is a known experimental limitation. HOLD, shadow mode, D2, and any other future feature are not presented as available.

**Conditional GO:** request one future experimental installation of the exact, hash-verified OBS ON artifact for the reusable plan above, subject to separate physical approval.

**NO-GO in the current host-only stage:** SD copying, camera installation, physical D1/AF/H.264 execution, lens movement, USB recovery claims, commit, push, release, or any claim of durable/complete logs without observed task/FIO completion and transfer integrity.
