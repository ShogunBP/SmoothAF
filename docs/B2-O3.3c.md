# SmoothAF V2 — B2-O3.3c: identidade persistente da observabilidade

**Status:** investigação e protótipo host-only concluídos; **NO-GO** para integração de produção, build ARM ou teste físico. As alterações locais existentes da B2-O3/B2-O3.3b foram preservadas. Não houve commit, push, acesso a VRAM/EDMAC/MVR real, execução D1, HOLD ou shadow mode.

## Objetivo e conclusão

O problema não é a capacidade de escrever mais campos no registro: é provar que dois registros pertencem à mesma sessão sem reutilizar uma identidade local após reinício. O ambiente Legacy 600D.102 não fornece, no código deste repositório, uma fonte demonstrável de identidade persistente entre boots.

A menor solução conceitualmente consistente é **D: evento aditivo de início de sessão + proveniência externa imutável**. Ela permite parear com segurança dentro de um escopo adquirido e identificado, mas não fabrica uma identidade global de câmera quando essa evidência não existe.

A recomendação permanece host-only até que o contrato de proveniência e a fonte do token sejam aceitos explicitamente. Portanto:

- **GO host-only:** modelo, parser fail-closed e testes determinísticos.
- **NO-GO produção/passive integration final:** não há ainda token confiável no firmware nem contrato operacional aprovado para gerar/preservar sidecar e fronteiras de arquivo.

### Tratamento dos casos exigidos

- **Compatibilidade histórica:** V1 continua `<IHHI6i` little-endian; eventos anteriores a `OBS_SESSION_START` são mantidos como opacos e nunca reinterpretados como identidade.
- **Espaço nos seis slots:** `payload[0]` contém `schema=1` e `kind=START` (`0x00000101`); `payload[1:5]` contém o token opaco de 128 bits como quatro palavras little-endian; `payload[5]=0` reservado. Não existe alteração nos seis slots de snapshot V1.
- **Módulo/câmera reiniciados:** criar novo token. Um token derivado de contador reiniciado, timestamp monotônico ou `sequence` é inválido como identidade global.
- **Reabertura/rotação:** cada arquivo/segmento deve ter `source_id` imutável; o consumidor pode associar segmentos ao mesmo token somente por metadata confiável. O filename numerado sozinho é fraco.
- **Concatenação:** sem fronteiras confiáveis, `AMBIGUOUS_PAIR`/`IDENTITY_UNAVAILABLE`; nunca parear através da concatenação.
- **Marker perdido:** sem sidecar com o token exato, os snapshots ficam `IDENTITY_UNAVAILABLE`; timestamp, `sequence`, `episode_id` e `logical_id` não são substitutos.
- **BEFORE/AFTER parcial:** `BEFORE_MISSING` ou `AFTER_MISSING`; não virar par estável.
- **Duplicado/contraditório:** `AMBIGUOUS_PAIR`, `stable_metadata=False`; uma classificação ambígua nunca vira `STABLE_METADATA`.
- **Wraps e reinício de contadores:** `sequence`, timestamp, `episode_id` e `logical_id` são metadados locais/ordenacionais. Wrap, drop ou recomeço não cria identidade e não é usado para cruzar sessões.
- **Drops/interleaving:** drops produzem incompletude; eventos de diferentes chaves podem intercalar dentro do mesmo source sem cruzamento, desde que a identidade e a chave wire sejam válidas.
- **Frame YUV:** identidade de sessão não demonstra independência dos frames BEFORE/AFTER. O relatório mantém `frame_independence_proven=False`.

## Contrato proposto

### Registro wire

Registro adicional, ainda não integrado a `src/`:

```text
record = <IHHI6i      # 36 bytes, ABI histórico
bytes  0.. 3: timestamp_ms   uint32 monotônico, sem valor de identidade
bytes  4.. 5: event_type     uint16 = 25 (OBS_SESSION_START, proposta)
bytes  6.. 7: episode_id      uint16 = 0
bytes  8..11: sequence        uint32, somente ordenação local
bytes 12..15: payload[0]      int32 bit pattern 0x00000101
bytes 16..19: payload[1]      token word 0, uint32 bits
bytes 20..23: payload[2]      token word 1, uint32 bits
bytes 24..27: payload[3]      token word 2, uint32 bits
bytes 28..31: payload[4]      token word 3, uint32 bits
bytes 32..35: payload[5]      0 reservado
```

Token válido: exatamente 16 bytes, não nulo. A implementação alvo deverá documentar a fonte de entropia/identidade e não poderá substituir essa fonte por contador reiniciado. O gerador do protótipo recebe valores injetados de forma explícita e falha quando a fonte acaba; ele não cria IDs sintéticos.

### Proveniência externa obrigatória

O consumidor deve fornecer, para cada arquivo/segmento adquirido:

1. `source_id` único e imutável para aquela aquisição (não apenas nome reutilizável);
2. token exato do marker, ou sidecar confiável que contenha o token exato se o marker não estiver presente;
3. relação explícita entre segmentos de rotação e a sessão, sem inferência por timestamp/nome;
4. indicação de que não houve concatenação sem fronteiras.

A chave efetiva do parser é `(source_id, session_token, episode_id, logical_id)`. O token tem escopo do source. Uma colisão de token em dois sources distintos não é aceita como prova de mesma sessão nem causa pareamento cruzado; se o source for reutilizado, o parser rejeita como ambíguo.

### Estados fail-closed

- `COMPLETE`: há BEFORE e AFTER, source imutável e token verificado.
- `BEFORE_MISSING` / `AFTER_MISSING`: somente um lado foi demonstrado.
- `IDENTITY_UNAVAILABLE`: falta source ou token verificável.
- `AMBIGUOUS_PAIR`: marker duplicado, marker contraditório, source reutilizado, chave duplicada ou metadata conflitante.

Somente `COMPLETE` pode produzir resultado de pareamento; mesmo assim `stable_metadata` depende dos campos V1 e `frame_independence_proven` continua falso. Estados não completos ou ambíguos não são convertidos em `STABLE_METADATA`.

## Fonte de identidade investigada

A investigação do repositório não encontrou no Legacy 600D.102:

- RTC/relógio absoluto serializado;
- serial da câmera, UUID ou API de hardware equivalente;
- RNG/entropia de hardware usada pelo módulo;
- contador persistente entre boots;
- boot ID persistente ou session UUID.

Evidências relevantes:

- `src/smoothaf_logger.h` define `timestamp_ms` como monotônico (`get_ms_clock` equivalent), e `docs/EDMAC_LOGGER_STUDY.md` registra wrap aproximado de 49 dias;
- `src/smoothaf_logger.c` mantém `sequence` em RAM, reinicializa o estado do logger e não o inclui no TSV;
- `src/smoothaf_build_id.h` identifica software/configuração, não câmera ou sessão, e o build ID não é serializado no log atual;
- FIO usa nomes numerados e rotação, mas filename não é identidade persistente;
- namespaces/generations de observabilidade são proteção em memória e não são serializados no V1.

Consequentemente, a implementação de produção não pode afirmar unicidade global de câmera/sessão sem uma fonte nova e aceita. O escopo demonstrável hoje é: **token opaco único somente dentro de um `source_id` confiável, com a unicidade entre boots dependente da fonte externa**.

## Protótipo e testes

Arquivos:

- `tools/b2o33c_identity.py` — contrato do marker, codificação/decodificação de 36 bytes, gerador por entropia injetada e `SessionPairer` fail-closed;
- `tests/test_b2o33c_identity.py` — testes host-only do contrato.

Cobertura validada:

- layout de 36 bytes e round-trip do marker;
- gerador sem contador e exaustão da fonte;
- pareamento somente após marker/token verificado;
- perda de marker e recuperação somente por token exato no sidecar;
- perda parcial de BEFORE/AFTER;
- concatenação com boundaries separados e ausência de cross-pair;
- reuso de `source_id` rejeitado;
- colisão/contradição de tokens e marcador duplicado;
- wraps de `sequence` e uso de IDs locais sem inferência de sessão;
- registros históricos tratados como opacos;
- `frame_independence_proven=False`.

Comando executado:

```text

git diff --check
```

A regressão conjunta preserva os contratos B2-O3.1/B2-O3.2 e o ABI V1. Não foi executado build ARM ou teste físico.

## Migração mínima futura de B2-O3.3

Quando — e somente quando — a origem do token e o contrato externo forem aprovados:

1. adicionar o novo tipo/evento e helper de emissão no logger, sem alterar o layout de 36 bytes;
2. emitir um marker por sessão lógica antes dos snapshots, aceitando que overflow/crash pode perdê-lo;
3. persistir o token/`source_id` em sidecar ou metadata de aquisição de forma atômica e não reutilizável;
4. atualizar o consumidor para abrir cada arquivo/segmento com boundary explícito e rejeitar cópias/concatenações sem provenance;
5. manter V1 e eventos históricos no parser dual, sem reinterpretar registros antigos;
6. adicionar testes C↔Python e de overflow/rotação antes de qualquer avaliação ARM.

O rollback é desativar a emissão/integração do marker e continuar consumindo V1; nenhum snapshot histórico precisa ser reescrito. Não adicionar V2 nem mexer em `main`, tags ou release nesta investigação.
